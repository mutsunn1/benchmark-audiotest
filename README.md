# 中文口语评测基准：传统声学引擎 vs Qwen-Omni

把调研报告里描述的两条技术路线真正搭起来，用**同一批音频**跑一遍，测出各自的准确率：

| 路线 | 实现 | 依据 |
|---|---|---|
| **传统 CAPT** | 本仓库自研的声学-音系学引擎 | 报告第 2–3 节：预加重/分帧 → MFCC+F0 → 强制对齐 → GOP/DTW → 五度 T 值 → 调型判定 |
| **Omni 直接评分** | Qwen-Omni（`qwen3-omni-flash`） | 报告第 4 节：端到端全模态模型直接打分 |

TTS 与 Omni 模型均使用 Qwen。核心待验证命题来自报告：
**Omni 模型会因语言先验而"脑补纠正"学习者的发音错误，表现为误收率（FAR）升高。**

---

## 1. 快速开始

### 离线跑通（不需要任何 API Key）

macOS 自带中文语音 `say`，整条管线可以完全离线跑完：

```bash
uv sync
uv run captbench run --tts say --scorers traditional
```

产物在 `data/results/`：`traditional.jsonl`（逐条判定）、`scorecards.json`（指标）、`report.md`（报告）。

### 接入 Qwen（需要 API Key）

```bash
cp .env.example .env      # 填入 DASHSCOPE_API_KEY
uv run captbench run --tts qwen --scorers traditional,omni
```

用 Qwen 时 `teacher` 音色与 `learner` 不同，因此这组数字是**跨说话人**条件下的结果；
用 `say` 时两者是同一音色的不同语速读数，属于同说话人条件。两者不可直接混比。

### 分步执行

```bash
uv run captbench build --tts say          # 合成语料
uv run captbench score --scorers traditional,omni --modes open,scripted
uv run captbench report                   # 出报告
uv run captbench info                     # 看当前配置
```

## 2. 基准是怎么设计的

### 2.1 构造性真值

不依赖人工标注。每个最小对立对（minimal pair）的两侧都用同一音色合成，然后指定一侧为
"学习者应该说的"，另一侧为"实际说出来的"：

```
expected=妈 (mā)   spoken=妈   -> 正确
expected=妈 (mā)   spoken=麻   -> 错误，维度=声调，T1->T2
expected=知 (zhī)  spoken=资   -> 错误，维度=声母，zh->z
expected=女 (nǚ)   spoken=你   -> 错误，维度=韵母，ü->i
```

因为替换是构造出来的，"正确/错误"以及错误落在声调、声母还是韵母上都是**已知的**。
覆盖范围：

- **声调**：4 个音节 × 4 个调 × 4 个目标调 = 16 条/音节，含全部 12 种替换对
- **声母**：zh/z、ch/c、sh/s、r/l、n/l，以及送气对立 b/p、d/t、g/k、j/q
- **韵母**：an/ang、en/eng、in/ing、ü/i、uo/e
- **语言陷阱句**：整句语境强烈预测某个词（"我想吃水饺"），音频实际说的是最小对立伙伴
  （"我想吃睡觉"）

### 2.2 learner / teacher 双轨录音（关键）

每条文本合成**两条**录音：

- `learner` —— 被评测的音频
- `teacher` —— 作为"标准发音"的参考，用于对齐、拟合声调原型、标定判定阈值

**两条必须不是同一份录音。** 如果学习者的"正确"音频就是参考音频本身，所有基于 DTW 的
比对都会得到 0 距离、全部判对，基准会自我恭维。`say` 后端靠不同语速区分——注意
`say` 会把语速量化到粗粒度档位（160 和 180 渲染出**字节相同**的音频），所以两个角色必须
落在不同档位；`build_corpus` 会检测并告警。

### 2.3 校准纪律

传统引擎的参数全部来自**参考资料**，从不来自被测音频：

| 参数 | 来源 |
|---|---|
| 说话人基频范围 (Fmin/Fmax) | 学习者本人的 8 条校准录音（4 个单字 + 2 个句子，从不计分） |
| 声调原型 | teacher 的正确读音，且**留出被测条目所属的最小对立组**（leave-one-contrast-out） |
| 段音判定阈值 | 该对立组两侧 teacher 读音的实测中点 |
| 句子语调原型 | 校准句的 teacher 读音（连读变调后） |

单字用单字原型、整句用句子原型：连读语流中的声调实现与孤立字差异很大，
用孤立字原型判整句会系统性失准（实测中这一点影响显著）。

### 2.4 为什么校准集里要有句子

孤立单字的基频跨度远小于整句。只用单字做校准，实测学习者范围是 150–274 Hz，
而同一说话人的整句达到 117–326 Hz，五度 T 值会被顶到 6.0（超出量程）并压扁区分度。
把句子纳入校准集后量程才覆盖真实分布。

## 3. 两个系统

### 3.1 传统引擎（`traditional.py`）

按报告描述自研，不含任何端到端模型：

```
音频 ─┬─ 预加重 0.97 → 25ms 汉明窗/10ms 帧移 → 26 梅尔滤波器 → 13 MFCC+Δ+ΔΔ (39维)
      ├─ Praat (parselmouth) 自相关基频跟踪 F0
      └─ 自相关周期度（用于 VOT 浊音起点判定）
                │
   模板 DTW 强制对齐 ──> 音节 [ts, te]（参考朗读的边界经 warping 路径映射到被测时间轴）
                │
      ┌─────────┴──────────┐
   超音段                  音段
   五度 T 值归一化          按对立组选定的物理线索：
   → DTW 匹配声调原型       平翘舌 → 摩擦段谱重心
   → 斜率/谷底/终点级特征    送气   → VOT
                           圆唇   → F3
                           前后鼻音 → F3-F2 收敛 (velar pinch)
                           无专用线索 → 最近参考模板 DTW
```

判定优先级：标定物理线索越界 > 声调原型不符 > 最近模板更近。

### 3.2 Omni 评分（`omni.py`）

同一段音频跑三种提示词，这一区分是实验的核心：

| 模式 | 提示词 | 测的是什么 |
|---|---|---|
| `open` | "转写你听到的音节（带声调数字）" | 纯感知能力，可与传统引擎的声调识别正面对比 |
| `context` | 只给交际场景，不给目标文本 | 语义是否把转写拉向"合理的那个词" |
| `scripted` | 给出目标文本，问发音对不对 | 标准 CAPT 场景，**语言陷阱就在这里** |

第三种如果模型信提示词胜过信音频，就会把替换判成正确。三种都跑才能区分
"没听清"和"听清了但顺从了提示词"——只跑一种的话这两种失败长得一模一样。

## 4. 指标

- **判定准确率**：能否区分正确发音与错误发音
- **误收率 FAR**：错误发音被判成正确的比例 ← 报告预测 Omni 在此劣化
- **误拒率 FRR**：正确发音被判成错误的比例
- **声调识别率**：音频中确实含某调时，命名该调的正确率（最公平的正面对比）
- **错误定位率**：已判错的条目里，维度（声调/声母/韵母）说对的比例
- **一致性**：同一段音频重复评测，结论是否一致（传统引擎确定性，Omni 是采样）
- **延迟**：每条中位耗时

## 5. 当前结果

见 `data/results/report.md`。离线（`say`，124 条）跑出的传统引擎基线：

| 指标 | 值 |
|---|---|
| 判定准确率 | **88.7%** (110/124) |
| 平衡准确率 | 85.8% |
| 误收率 FAR | **6.0%** (5/84) |
| 误拒率 FRR | 22.5% (9/40) |
| 声调识别率 | **69.0%** (40/58) |
| 错误定位率 | 93.7% |
| 中位延迟 | < 10 ms |

分题型：

| 题型 | n | 准确率 | 误收率 |
|---|---|---|---|
| 声母 (initial) | 40 | 97.5% | 0.0% |
| 声调 (tone) | 52 | 90.4% | 10.4% |
| 韵母 (final) | 24 | 83.3% | 0.0% |
| 陷阱句 (trap) | 8 | 50.0% | 0.0% |

声调识别混淆矩阵（实际 → 识别）：

| 实际 \ 识别 | T1 | T2 | T3 | T4 |
|---|---|---|---|---|
| T1 | 16 | 0 | 0 | 0 |
| T2 | 0 | 6 | 0 | 6 |
| T3 | 0 | 0 | 5 | 10 |
| T4 | 0 | 0 | 2 | 13 |

**读法**：

- 阴平 100% 可分；**失分几乎全部集中在"被识别为去声"**——这是 `say` 把上声实现成
  低降调（21）而非完整 214 的直接后果，上声与去声同形，只能靠起点高度区分。
- 声母最好（97.5%）：平翘舌靠摩擦段谱重心、送气靠 VOT，两条物理线索在这个音色上
  分离度都足够。
- 声调**识别**只有 69%，但声调**检测**有 90.4%——即使把 T2 错认成 T4，只要与期望的
  T1 不符就仍能判出"这条错了"。
- 陷阱句对照句误拒率 100%：整句判定取所有音节的最强证据，非焦点音节的误判会拖垮整句。
  句子语调原型仅由 2 条校准句拟合（spread 0.51/0.66，远大于单字的 0.06/0.18），
  这是当前最薄弱的一环。

> Omni 一侧的数字需要 `DASHSCOPE_API_KEY` 后运行 `--scorers omni` 才会出现在同一张表里。

## 6. 已知局限

1. **合成语料而非真实学习者**。错误项是干净的范畴替换；真实学习者的偏误是连续渐变的。
   本基准测的是"能否区分范畴替换"，不是"能否给出口音分数"。要测后者需要引入真实
   学习者语料（如 Speechocean762）。
2. **传统引擎是参考实现，不是商业引擎**。没有接讯飞/SpeechSuper，绝对水平不代表商业
   引擎水平——商业引擎用 DNN-HMM 在海量母语者语料上训练，这里没有。
3. **上声/去声混淆是传统引擎的主要失分点**。`say` 把上声实现为低降调（21）而非完整
   214，与去声同形，只能靠起点高度区分。
4. **跨说话人未验证**。`say` 后端下 learner/teacher 同音色不同语速。`--tts qwen` 会变成
   跨音色，数字需要重跑才能比较。
5. **陷阱句对照句误拒率偏高**，原因是引擎对所有音节取最强证据，非焦点音节的判断也会
   影响整句结论。

## 7. 命令参考

```bash
captbench build   [--tts say|qwen] [--families tone,initial,final,trap] [--limit N] [--force]
captbench score   [--scorers traditional,omni] [--modes open,context,scripted]
                  [--items id1,id2] [--limit N] [--repeats 3] [--temperature T]
captbench report
captbench run     # build + score + report
captbench info
```

`--repeats N` 会重复评测 `--consistency-n` 条样本，用于测量 Omni 的采样稳定性。
